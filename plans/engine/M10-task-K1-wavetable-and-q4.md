## Context for a fresh agent

Architecture Q4 asks whether `Instrument` (`crates/starplayer-engine/src/instrument.rs`)
survives a non-sample instrument. Master-plan decision 1 predicts the answer — it survives
with `&mut self` — and decision 2 says a wavetable is the cheapest instrument to prove it
with, because a wavetable is **sample-backed**: each table frame is a single-cycle looped
sample in an ordinary `Module` built with `ModuleBuilder` (`crates/starplayer-model/src/builder.rs`),
and playing it is an ordinary voice. The mixer does not change; the goldens cannot move.

What a wavetable needs that `SampleInstrument` does not: a **position** in the table that
can move while a note sounds (the morph), an **ADSR** on volume, and therefore per-voice
state that outlives `note_on` and is advanced on `control_tick`. That state is the parallel
array pattern the format crates use (§5.3: `Box<[State]>` indexed by `VoiceId::index()`,
validated by the generation) — which needs `&mut self`. Making that change, with the
first instrument that needs it, **is** the Q4 answer; record it in §5.3 and §12.

## Deliverables

### 1. The trait change (engine)

`Instrument`'s four methods take `&mut self`. `InstrumentRack` already owns
`Box<dyn Instrument>`s; update its call sites and the two existing implementations (no
behaviour change; their bodies do not use the mutability). Add
`InstrumentRack::with_instruments(Vec<Box<dyn Instrument>>)` (or `push_instrument`) so a
rack can be built from synths rather than from a module, and `InstrumentRack::empty()`
grows to accept a `pcm`-less engine. Update §5.3's trait listing and §12 Q4:
"**Settled in M10-K1** — the trait survives; its methods became `&mut self` so an
instrument can own per-voice state in the parallel-array pattern".

### 2. `crates/starplayer-synth` (`no_std + alloc`)

A new crate → engine, model, dsp, core. Feature `wavetable` (default off in the facade;
the facade gains `synth-wavetable`). `NO_STD_CRATES` in `xtask` and the purity job cover it.

- **`Adsr`** (`adsr.rs`): attack/decay/sustain/release in control ticks (the rack's
  ~1 ms), linear attack, exponential-shaped decay and release via `pow2_q24` steps (no
  transcendental), output `U0F16`, states `Idle/Attack/Decay/Sustain/Release/Done`,
  `note_off` enters release from any state, `advance()` once per tick. Exactly the
  frames-since-change discipline the mixer's ramps use, so a note is a pure function of
  ticks. This runner is shared by K2, K3, K4, K6.
- **`WavetableBank`**: `N` frames of `2048` samples each (the wavetable convention;
  configurable at build), each stored as a forward-looped single-cycle sample in a
  `Module` built through `ModuleBuilder::add_sample` at a reference rate chosen so that
  `REFERENCE_NOTE` (60) plays the cycle at 261.63 Hz through the existing linear-frequency
  pitch path (`rebend`'s table). Built once, off the audio thread; `Arc<Module>`-shared
  like every module. Ship three built-in banks generated by `const`/`fn` code (basic
  waves: sine → triangle → saw → square across 8 frames; a formant series; a PWM sweep)
  and a `from_frames(&[&[i16]])` constructor for user tables.
- **`WavetableInstrument: Instrument`**: per-voice state `{ voice: VoiceId, position: u16 (Q8.8 frame index), adsr: Adsr, base_step: Step, bend_cents: i16 }`
  in a `Box<[Option<State>]>` sized to `MAX_VOICE_CAPACITY`. `note_on` triggers the sample
  for the *integer* table frame at the current position and starts the ADSR; the
  **morph** between frames is a crossfade of two voices when the position is fractional
  (`note_on` allocates a second voice at the next frame, gains split by the fraction) —
  or, if the pool is short, one voice at the nearest frame; state records which.
  `control_tick` advances the ADSR and writes `VoiceParam::Volume` (velocity × ADSR ×
  CC7 is the rack's business — the instrument writes the ADSR-shaped velocity and the rack
  keeps applying CC7 as it does today) and, when the position is moving (a morph LFO or a
  CC), re-splits the pair's gains. `note_off` releases; when the ADSR reaches `Done` the
  voices are stopped (`DirtyBits::STOP`) and the state slot cleared. `set_bend` re-derives
  the step as `rebend` does.
- **Controllers**: CC 74 (position, 0–127 → frame span), CC 73/72 (attack/release),
  CC 1 (morph LFO depth) via a `controller(&mut self, channel, number, value)` hook —
  either a new trait method with a default no-op or the rack forwarding `Controller` events
  it does not own to the instrument. Choose the former if it keeps the rack untouched
  otherwise; say why.

### 3. Hosts

`Player::load_synth(SynthKind::Wavetable(bank))` builds a rack of one instrument on every
MIDI channel and a `MidiSource` over the live queue, like `midi_only` does for a module;
the CLI's `play --synth wavetable[:bank]` and the web page's MIDI panel gain the option.
The keyboard and Web MIDI paths from M4-E6 need no change.

### 4. Proof

- **Block-size determinism**: `crates/starplayer-engine/tests/midi_source.rs` (or a new
  test in the synth crate) plays a note script through the wavetable at every block size
  on both paths; byte-identical.
- **Spectral**: a note at 60 on the sine frame produces a 261.63 Hz peak with harmonics
  below −60 dB; the saw frame's harmonic series falls at 6 dB/octave ± 1 dB (an `f64`
  DFT under `std` in the test).
- **ADSR**: the envelope's value after `n` ticks matches a closed-form reference within
  1 LSB of `U0F16`, and `note_off` from attack goes to release without a jump.
- **Morph**: with position at 0.5 the pair's gains sum to unity; sweeping position from
  0 to 1 over 1 s has no sample-to-sample step above the crossfade's per-tick slope.
- **RT-safety**: `render_allocation.rs` with the wavetable in the mux and a note burst.
- `cargo xtask goldens --check` unchanged (nothing in the mixer moved).
- `no-std-purity` with `starplayer-synth` in the list; `wasm-build`; `clippy`.

## Research points

1. **Does the wavetable need `&mut self` at all?** It does (the ADSR and the morph
   position); if you find a way to keep `&self` by moving the state into the rack, argue
   it, but the master plan's expectation is the trait change — a rack that knows every
   synth's state shape is the wrong layering.
2. **Morph by two voices vs. a mixer change**: two voices cost pool slots and split the
   pan law; a per-voice second region with a crossfade in the kernel would be a mixer
   change and a goldens question. Two voices for K1; note whether the click-free crossfade
   holds when the pair is stolen unevenly.
3. **Control-rate aliasing**: the ADSR steps at ~1 ms; a 1 ms attack is one step. Whether
   to let the mixer's 64-frame gain ramp smooth it (it will, since every `Volume` write
   ramps) — verify there is no zipper noise on a fast attack.
